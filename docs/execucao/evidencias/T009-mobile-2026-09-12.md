# T009 — evidência mobile de push (2026-09-12)

## Resultado

Implementação mobile interna pronta para revisão r2: `expo-notifications` foi adicionado ao app Expo SDK 54, com plugin nativo, fluxo explícito em **Notificações → Ativar push**, token Expo registrado via cliente autenticado e revogação canônica não bloqueante no logout.

## Contrato mobile

- Registro: `POST /me/push-tokens` com `{device_id, token, platform, provider: "expo"}`; a resposta precisa conter `id` numérico.
- Revogação canônica: `DELETE /me/push-tokens/{id}` com Authorization capturada antes do logout.
- O cliente só usa caminhos relativos fixos; não há URL de endpoint configurável nem possibilidade de SSRF.
- `EXPO_PUBLIC_EXPO_PROJECT_ID` tem precedência; fallback para `expo.extra.eas.projectId`/`easConfig.projectId`.

## Comportamentos cobertos

- Permissão só é solicitada em Android/iOS, em dispositivo físico, após autenticação e ação explícita.
- Web, simulador, permissão negada, project ID ausente e falhas de rede retornam estado controlado, sem crash ou loop.
- `device_id` é UUID estável persistido no armazenamento seguro nativo; o token nunca é escrito em log.
- Registro armazena `id`, `userId`, token e device em armazenamento seguro apenas para permitir revogação; falha preserva a pendência para retry somente no próximo login do mesmo usuário.
- IDs de revogação são enfileirados persistentemente por `userId` sem tokens; múltiplos IDs são drenados antes de qualquer novo POST do mesmo usuário. Falha parcial mantém somente os IDs não confirmados e retorna `pending_revocation`, sem substituir o registro anterior.
- Logout inicia a revogação com Authorization explícita, sem aguardá-la; respostas 204/404 removem a pendência e outras falhas a preservam.
- Listeners nativos de recebimento/press têm cleanup; somente `concurso_id`/`concursoId` inteiro positivo gera a rota `/concurso/{id}`.
- Cold-start usa `getLastNotificationResponseAsync()` com a mesma validação e chave idempotente de resposta; listener e last response coincidentes navegam uma única vez.
- Expo Go é reportado separadamente como exigindo development build.
- Reautenticação reutiliza o mesmo `device_id` e pode registrar o token novamente.

## Verificação

Executados na pasta `mobile/`:

```text
npx tsc --noEmit                         PASS
node --test tests/*.test.cjs             39 passed, 0 failed
```

Os testes mockam `expo-notifications`, armazenamento seguro, plataforma e cliente HTTP e cobrem registro/revogação com ID numérico e rota exata, fila com múltiplos IDs/falha parcial/restart, retry/ownership por usuário, web, simulador, Expo Go, permissão negada, project ID ausente, listeners/cleanup, cold-start válido/inválido/duplicado, deep-link estrito, endpoint relativo e reautenticação. Não houve envio de push real nem abertura de dispositivo/emulador.

## Dependência

`expo-notifications@^0.32.17` foi instalado com npm e o `mobile/package-lock.json` foi atualizado (versão resolvida compatível com Expo SDK 54). O `npm install` reportou vulnerabilidades já existentes no grafo; nenhuma correção automática foi aplicada.
